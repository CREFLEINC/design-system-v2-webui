# 조합 패턴 (Patterns)

여러 화면에서 반복되는 **기존 컴포넌트 조합의 기본 동작 규범**을 정한다.
코드는 제품이 소유하고, 규범은 DS가 소유한다.

## 이 문서의 범위

| 문서 | 무엇을 다루나 |
|---|---|
| `docs/COMPONENTS.md` | 무엇이 **있는지** — 인벤토리(생성 문서) |
| `docs/component-conventions.md` | 컴포넌트를 **만드는** 관례 — DS 내부용 |
| `docs/component-requests.md` | 없는 것을 **요청하는** 절차 — a·b·c·d 분류 |
| `docs/patterns.md` (이 문서) | 있는 것을 **조합해 쓰는** 규범 — 제품용 |

여기 실린 조합은 `component-requests.md`의 **`c`(조합)로 남는다.** 패턴 등재는 DS가 그
조합을 컴포넌트로 만들겠다는 뜻이 아니다 — 구현과 코드 소유는 그대로 제품 repo에 있다.
바뀌는 것은 하나다: **그 조합의 표준형을 DS가 유지한다.**

컴포넌트로 만들지 않는 이유는 `component-requests.md`에 적힌 것과 같다. 조합의 정책을
config prop으로 흡수하면, 일부 화면만 설계된 시점의 판단이 API로 굳는다.

## 패턴 등재 기준

두 조건을 **모두** 만족하면 이슈로 패턴 등재를 요청한다.

1. 같은 조합이 **세 곳 이상**에서 쓰인다.
2. 화면마다 갈리는 것이 렌더가 아니라 **동작·정책**이다 — 초기화 범위, 조회 시점, 상태 유지 등.

세 곳은 `component-requests.md`의 `d` 승격 문턱과 같은 숫자다. `d`는 세 곳에서 **코드를
승격**하고, `c`는 세 곳에서 **규범을 등재**한다. 팀이 외울 규칙은 하나다.

갈리는 것이 렌더뿐이면(간격·정렬·라벨 문구) 패턴이 아니다. 동작이 갈리는데 세 곳에
못 미치면 아직 이르다 — 두 번째 사용처까지는 무엇이 표준형인지 알 수 없다.

패턴은 모두 같은 다섯 절로 쓴다: **적용 대상 / 조합 부품 / 기본 동작 / 하지 말 것 / 관련.**
"기본 동작"의 각 항목에는 기본값 하나와 이탈 조건을 함께 적는다 — "상황에 따라 다르다"로
쓰면 등재하지 않은 것과 같다. 이탈은 금지가 아니지만, 이탈하는 화면은 사유를 화면 스펙에
남긴다.

## 패턴: 검색·필터 바

### 적용 대상

목록을 가진 화면 위에 붙는 조회 조건 영역. 검색어 입력 + 조건 선택 여러 개 + 적용된 조건
표시 + 조회·초기화로 이루어진다. 확인된 사용처 12곳.

### 조합 부품

| 역할 | 컴포넌트 | 핵심 prop |
|---|---|---|
| 검색어 입력 | `SearchInput` | `onSearch`(Enter 확정), `onClear`, `loading` |
| 조건 선택 | `Select` | `options`, `value`, `onChange`, `placeholder` |
| 적용된 조건 표시 | `Chip` (`variant="status"`) | `onRemove`, `removeLabel` |
| 조회·초기화 | `Button` | `variant`, `loading` |
| 결과 없음 | `EmptyState` | `title`, `description`, `action`, `live` |

`Chip`의 `variant="filter"`(`selected`·`onSelectedChange`)는 조건을 **고르는** 칩이다.
이미 적용된 조건을 **보여주는** 자리에는 쓰지 않는다(아래 ①).

### 기본 동작

트리거 모델은 한 문장이다: **편집은 모아서 적용, 해제는 즉시.**
조건 편집(입력·`Select` 변경)은 조회로 일괄 적용하고, 이미 적용된 조건의 해제(칩 제거·
초기화)는 그 자리에서 재조회한다. 아래 다섯 항목은 전부 이 문장에서 나온다.

| 갈리는 지점 | 기본 동작 | 이탈 조건 |
|---|---|---|
| ① 조건 칩 | 기본값과 다른 **적용된** 조건만 `Chip`으로 보인다. 편집 중(아직 조회하지 않은) 값은 미러하지 않는다. `onRemove`로 X를 달고, `removeLabel`에는 무엇이 지워지는지 담는다(예: `"분류 조건 제거"`). 칩 제거 = 그 조건만 기본값 복귀 + **즉시 재조회** | 조건이 하나뿐이고 그 컨트롤이 항상 화면에 보이면 칩을 생략한다 |
| ② 초기화 범위 | **화면 진입 시의 기본 조건으로 복귀**한다. 전부 빈 값이 아니다 — 기본 조건이 있는 화면에서 초기화는 전체 해제가 아니다. 초기화 직후 즉시 재조회 | 기본 조건이 없는 화면에서는 결과적으로 전체 해제와 같아진다. 규칙은 그대로다 |
| ③ 조회 시점 | 서버를 왕복하는 조회는 **조회 버튼**이 기본이다. `SearchInput`의 Enter(`onSearch`)는 조회 버튼과 동일한 트리거로 잇는다. 이미 받아 둔 목록을 클라이언트에서 거르는 경우에만 입력 즉시 반영하고 **300ms 디바운스**를 건다. 칩 제거·초기화는 언제나 즉시 | 서버 왕복이 없고 결과가 항상 한 화면에 들어오는 소량 목록이면 버튼 없이 즉시 + 디바운스 |
| ④ 결과 없음 | `EmptyState`로 **두 상태를 구분**한다. (a) 조건이 기본값인데 결과 없음 → "아직 등록된 항목이 없습니다" + `action`에 생성 유도. (b) 조건을 적용했는데 결과 없음 → "조건에 맞는 결과가 없습니다" + `description`에 적용된 조건 요약 + `action`에 초기화. 조회 결과로 바뀌어 나타나는 빈 상태이므로 `live`를 켠다 | (a)에서 생성 권한이 없는 사용자에게는 `action` 없이 문구만 |
| ⑤ 조건 유지 | 목록 → 상세 → 뒤로 돌아오면 **조건과 페이지를 유지**한다. 저장 위치는 **URL 쿼리 파라미터**를 권장한다 — 뒤로가기·새로고침·링크 공유가 모두 같은 결과를 낸다. 전역 내비게이션으로 목록에 **새로 진입**하면 기본 조건으로 시작한다 | URL에 담기 어려운 조건(과도하게 길거나 노출하면 안 되는 값)만 세션 저장소로 옮기고, 그 경우에도 뒤로가기 복원을 직접 확인한다 |

⑤가 가장 자주 어긋난다. 세션 메모리에만 담으면 화면 안에서는 멀쩡해 보이지만 브라우저
뒤로가기·새로고침에서 조건이 사라진다. "돌아왔다"와 "새로 왔다"를 구분하는 기준은
**어디서 왔는가**이지 저장소에 값이 남아 있는지가 아니다.

### 하지 말 것

- 결과가 없을 때 필터 바를 숨긴다 — 조건을 바꿀 수단이 함께 사라진다.
- 칩이 편집 중인 값을 미러한다 — 표시된 조건과 실제 조회 조건이 어긋난다.
- 상세에서 목록으로 돌아왔을 때 조건을 초기화한다.
- 초기화가 화면의 기본 조건까지 지운다.
- 화면마다 트리거 모델을 다르게 섞는다 — 어떤 목록은 즉시, 어떤 목록은 버튼이면
  사용자는 화면마다 다시 배운다.

### 관련

- 이슈 #43 — 등재 근거(사용처 12곳, 갈리는 항목 5가지).
- `docs/component-requests.md` — `c`(조합) 유형과 패턴 등재 통로.

## 패턴: 읽기 전용 구획 배치

### 적용 대상

폼 화면에서 **한 구획(섹션) 전체**가 편집 불가한 경우 — 확정 후 잠금, 권한 없음, 상위
상태에 종속 등. 필드 하나가 잠기는 경우는 패턴이 아니라 `TextField`의 `disabledReason`
하나로 끝난다.

### 조합 부품

| 역할 | 무엇을 쓰나 | 비고 |
|---|---|---|
| 구획 경계·제목 | 네이티브 `<fieldset>` + `<legend>` | 구획 래퍼 컴포넌트를 만들지 않는다 |
| 구획 잠금 사유 | legend 아래 **항상 보이는 DOM 텍스트 1곳** | `<fieldset>`에 `aria-describedby`로 연결 |
| 구획 안의 컨트롤 | `TextField`·`Select`·`Checkbox` 등 | 각각에 `disabled`를 **명시적으로** 전달 |
| 필드별 사유 | `TextField`의 `disabledReason` | 구획 사유와 다를 때만 |
| 화면 전체가 조회 전용 | `Table`·`DiffRow` 등 | 애초에 폼으로 만들지 않는다 |

### 기본 동작

먼저 `disabled`인지 `readOnly`인지 가른다. 값 열람이 목적이면 `readOnly` — 포커스와
복사가 되고, 부가 설명은 `helperText`로 충분하며 잠금 사유가 필요 없다. 상태나 권한 때문에
편집이 **차단된** 것이면 `disabled` + 사유다. 화면 전체가 조회 전용이라면 그건 잠긴 폼이
아니라 상세 뷰다.

`readOnly`는 `<input>`을 쓰는 컨트롤(`TextField` 등)의 네이티브 속성이다. 트리거가 버튼인
`Select`에는 없고, 네이티브 체크박스의 `readOnly`는 토글을 막지 못한다. 이런 컨트롤에서
편집이 차단된 것이 아니라 값을 보여 주기만 하면 되는 자리라면, 폼 컨트롤을 잠그지 말고
값 표기로 낸다.

`disabled` 컨트롤은 포커스를 받지 못하므로 사유를 `Tooltip`으로만 전달하면 키보드·
스크린리더 사용자가 도달할 수 없다(`docs/component-conventions.md` 접근성 절). 그래서
사유는 항상 보이는 DOM 텍스트로 렌더하고 `aria-describedby`로 잇는다. 필드 단위의 기준
구현이 `TextField`의 `disabledReason`이고, 이 패턴은 같은 원칙을 구획 단위로 확장한다.

두 층위의 분담은 **사유가 몇 개인가**로 정한다.

| 상황 | 사유를 어디에 두나 |
|---|---|
| 구획 전체가 **한 가지 사유**로 잠김 | 구획 헤더에 **한 번만**. 개별 필드의 `disabledReason`은 쓰지 않는다 |
| 구획 일부만 잠기거나 필드마다 사유가 다름 | 필드 단위 `TextField`의 `disabledReason` |
| 구획 사유가 있고 특정 필드만 사유가 다름 | 두 층위를 함께 쓴다 — 필드 사유가 구획 사유와 **다를 때만** |

시각·ARIA 상태를 `<fieldset disabled>`의 상속에 맡기지 않는다. 네이티브 상속은 컨트롤을
비활성화하지만, DS 컴포넌트의 disabled 표현(라벨 뮤트·보더 상태와 `disabledReason` 렌더)은
각 컴포넌트가 받은 `disabled` prop에 걸려 있어 상속만으로는 켜지지 않는다. 구획 안의
컨트롤에 `disabled`를 그대로 내려준다.

### 하지 말 것

- 같은 사유를 필드마다 반복한다 — 화면에도 스크린리더에도 같은 문장이 필드 수만큼 쌓인다.
- 사유를 `Tooltip` 단독으로 전달한다 — disabled 컨트롤은 포커스를 받지 못한다.
- 편집 가능한 구획과 나란히 있는 폼에서 읽기 전용 구획만 평문 텍스트로 렌더한다 —
  라벨 위치와 정렬이 어긋나 폼을 훑는 흐름이 끊긴다.
- 값 열람이 목적인데 `disabled`를 쓴다 — 복사도 막히고, 없는 잠금 사유를 지어내게 된다.
  입력 계열이면 `readOnly`가, 아니면 값 표기가 맞다.

  배치가 이 패턴이다.
- `docs/component-conventions.md` 접근성 절 — disabled 컨트롤의 부가 정보 원칙.
